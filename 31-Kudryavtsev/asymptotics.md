# Расчёт асимптотической сложности

Обозначения: n — число обрабатываемых элементов, m — ёмкость таблицы,
u — число уникальных элементов, q = min(k, n).
Стоимость сравнения элементов, equals и hashCode здесь считается O(1).
Для строк длины L отдельное сравнение или вычисление ещё не закешированного хеша может стоить O(L).

## 1A, 1B — очередь с приоритетом

Двоичная куча высоты O(log n) хранится в массиве.

| Операция | Время | Причина |
|---|---|---|
| `add` без расширения | O(log n) | Просеивание по одной ветви к корню |
| `add` с расширением | O(n) | Копирование массива плюс просеивание |
| `add` амортизированно | O(log n) | Сумма копирований при удвоении: 16 + 32 + ... < 2n |
| `poll` | O(log n) | Перенос последнего элемента и просеивание по одной ветви вниз |
| `peek`, `size`, `isEmpty` | O(1) | Чтение вершины или поля размера |

Память — O(n). Min-heap и max-heap отличаются только знаком порядка сравнения.
В условии add указан как O(log n); с обязательным динамическим расширением это амортизированная оценка.

## 2A, 2C — хеш-таблица

При хорошем распределении хешей, загрузке до 0.75 и коротких цепочках из живых и удалённых ячеек
поиск и вставка ожидаемо проверяют O(1) ячеек.
Перехеширование с ростом ×2 ожидаемо занимает O(m); за серию вставок расходы на рост амортизируются.
Поэтому ожидаемая амортизированная стоимость put — O(1), а get/containsKey/remove — ожидаемо O(1).

Худший случай поиска, containsKey и удаления — O(m), поскольку поиск проверяет максимум m ячеек.
Вставка без расширения — O(m). Расширение с коллизиями может стоить O(m²):
каждая переносимая запись снова проходит свою цепочку. Соответственно худшая стоимость одного put с ростом — O(m²).
`size` и `capacity` всегда O(1). Память — O(m), включая старые и новые массивы во время расширения.
После большого числа удалений m может быть существенно больше числа живых записей: таблица не сжимается.
Без очистки DELETED ожидаемая O(1) оценка не гарантируется для произвольной истории удалений.

Для CollisionKey все записи попадают в одну цепочку.
Вставка n записей требует суммарно O(1 + 2 + ... + n) = O(n²), включая геометрическую серию расширений.
Поиск и удаление всех n ключей также занимают O(n²). Отдельный поиск при длинной цепочке — O(n).

## 3A — Top-K

В куче не более q элементов. Каждый из n входных элементов требует сравнение с минимумом,
а при необходимости — poll и add за O(log(q + 1)).
Извлечение результата занимает O(q log(q + 1)), что не превышает O(n log(q + 1)).
Итого **O(n log(q + 1)) времени и O(q) дополнительной памяти**, включая результат.
При 2 <= k <= n это требуемое O(n log k); при k = 1 время O(n), при k = 0 — O(1).
При k > n не выделяется массив длины k: возвращаются все n элементов.

## 3C — уникальные элементы

Один проход по n элементам. Для каждого — containsKey и, при первом появлении, put и append.
При обычном распределении хешей время **O(n) ожидаемо**, память **O(u)** для таблицы и списка.
При искусственных коллизиях суммарное время может быть O(n²), включая перехеширование.
Число пробирований зависит и от equals/hashCode входных объектов.

## Вспомогательный ArrayListCustom

`get` и `size` — O(1). `add` — O(1) амортизированно и O(n) в момент расширения.
Массив растёт вдвое: сумма ранее скопированных элементов меньше удвоенного конечного размера.
Память — O(n); лишняя ёмкость и промежуточные массивы отражены в измерениях выделений памяти.
